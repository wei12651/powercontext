# 第 4 讲 索引与查询优化

## 4.1 为什么需要索引

索引的本质是把「全表扫描」换成「按有序结构定位」。没有索引时，一条 `WHERE id = 42` 必须把每一行读出来比较，代价随行数线性增长；建立 B+ 树索引后，代价变成树高次磁盘页读取，通常是 3 到 4 次。

代价是写放大：每次 INSERT / UPDATE / DELETE 都要同步维护索引。所以索引不是越多越好，判断标准是「读多写少、且过滤性强的列才值得建」。过滤性可以用基数（该列不同值的个数）粗略衡量，像性别这种只有两三个取值的列，单独建索引几乎没有收益。

## 4.2 B+ 树为什么适合做磁盘索引

磁盘的随机读是毫秒级、顺序读是微秒级，差了三个数量级，所以索引结构必须尽量把「一次定位」压缩成少数几次页读取。B+ 树在这点上做对了三件事：

第一，非叶子节点只存键和指针，不存数据，因此一个 16 KB 的页可以塞进几百个键，扇出很大，树高被压到 3 至 4 层。第二，所有数据都在叶子节点，且叶子之间用双向链表相连，范围查询和 ORDER BY 可以顺着链表顺序扫，把大量随机读变成顺序读。第三，节点插入时通过分裂维持平衡，最坏情况依然是 O(log n)。

对比 B 树：B 树的非叶子节点也存数据，扇出变小、树变高，而且范围查询要在树中反复回溯。对比哈希索引：哈希只支持等值查询，不支持范围和排序，还会因为哈希冲突退化。所以关系型数据库的默认索引几乎都是 B+ 树。

## 4.3 最左前缀与联合索引

联合索引 `(a, b, c)` 的键是按 a、再按 b、再按 c 排序的。这决定了它能被用在哪些查询上：

- `WHERE a = 1` 可以用，`WHERE a = 1 AND b = 2` 可以用，三个都用也可以。
- `WHERE b = 2` 用不上，因为 b 在整体排序里不是第一关键字。
- `WHERE a = 1 AND c = 3` 只能用到 a，c 无法走索引定位，但如果是覆盖索引仍可避免回表。
- `WHERE a > 1 AND b = 2`，范围条件之后的列失去定位能力，这是「最左前缀」最容易被忽略的一条。

设计联合索引时把等值过滤的列放前面、范围过滤的列放后面，再把经常出现在 SELECT 里的列加到末尾做覆盖索引，能显著减少回表。

## 4.4 回表、覆盖索引与索引下推

二级索引的叶子节点存的是主键值，不是整行。通过二级索引找到主键后还要再回主键索引取整行，这一步叫回表。回表是随机读，代价很高。

如果查询需要的列全部在索引里，就不需要回表，这叫覆盖索引。例如 `SELECT b FROM t WHERE a = 1` 在索引 `(a, b)` 上就是覆盖索引。

索引下推（Index Condition Pushdown）是把 WHERE 中能用到索引列的判断提前到存储引擎层做，减少回表次数。比如 `WHERE a = 1 AND b LIKE '张%'` 在 `(a, b)` 索引上，b 的 LIKE 判断可以在索引层完成，只对真正满足条件的行回表。

## 4.5 如何看执行计划

用 `EXPLAIN` 看执行计划，重点看四列：type 反映访问方式，从好到坏大致是 const、eq_ref、ref、range、index、ALL；key 表示实际用了哪个索引；rows 是预估扫描行数；Extra 里的 Using index 表示覆盖索引，Using filesort 表示需要额外排序，Using temporary 表示用了临时表。

如果 type 是 ALL 且 rows 很大，通常是缺索引或者索引失效。索引失效的常见原因包括：在索引列上做函数运算或隐式类型转换、使用前导通配的 LIKE、OR 连接的列没有全部建索引、以及优化器估算成本后主动放弃索引。
